# Шаблоны ответов архитектора

Библиотека из 12 шаблонов для типовых писем и ответов: запрос схемы, обоснование решения, отказ с альтернативой и другие рабочие ситуации. Код — `src/templates/library.js`, тесты — `test/templates/library.test.js`.

Шаблоны не отправляются сами и не меняют черновик молча: `fillTemplate()` возвращает готовый текст, который архитектор вставляет в черновик (например, собранный `src/drafts/build.js`) и правит под ситуацию.

## Зачем

- не писать одно и то же письмо заново;
- не забыть обязательные элементы: срок, источник, следующий шаг;
- честно показывать, каких данных ещё нет, вместо правдоподобных догадок.

## Список шаблонов

| id | Название | Когда применять |
| --- | --- | --- |
| `diagram-request` | Запрос схемы | Нужна актуальная схема компонентов или потоков данных перед обсуждением решения. |
| `decision-rationale` | Обоснование решения | Нужно объяснить, почему выбрано решение и на чём оно держится. |
| `refusal-with-alternative` | Отказ с альтернативой | Запрос выполнить в текущем виде нельзя, но есть рабочий обходной вариант. |
| `data-request` | Запрос данных | Для проработки вопроса не хватает данных или выгрузки из системы-источника. |
| `integration-approval` | Согласование интеграции | Интеграция проверена и готова к подтверждению принимающей стороной. |
| `deadline-shift` | Перенос срока | Срок срывается по объективной причине и нужен явный перенос с планом. |
| `escalation` | Эскалация | Вопрос заблокирован и не решается на текущем уровне ответственности. |
| `security-requirements` | Новые требования безопасности | Появились обязательные требования ИБ, которые меняют решение или сроки. |
| `cafo-question` | Вопрос по КАФО | Данные на странице КАФО расходятся с фактами или требуют подтверждения. |
| `committee-request` | Запрос на комитет | Решение требует обсуждения и фиксации на архитектурном комитете. |
| `answer-analysts` | Ответ аналитикам | Аналитики просят подтвердить вводные для требований или модели данных. |
| `answer-adjacent-team` | Ответ смежной команде | Смежная команда задала вопрос по границам ответственности или интеграции. |

## Как заполнять

```js
import { listTemplates, getTemplate, fillTemplate } from './src/templates/library.js'

listTemplates() // [{ id, title, when }, ...] — без тел

const template = getTemplate('decision-rationale')
template.body // текст с подстановками {{request}}, {{found}}, {{deadline}}, {{source}} и т. п.

const { text, missing } = fillTemplate('decision-rationale', {
  request: 'согласовать обмен заказами',
  decision: 'использовать очередь событий',
  found: 'сервис заказов уже публикует события',
  source: 'page_id=42; version=7',
  deadline: '1 декабря'
})
```

- Ключи — имена подстановок без фигурных скобок: `request`, `found`, `deadline`, `source` и др.
- Значение подставляется как есть, без HTML-экранирования: это обычный текст письма, а не разметка.
- Пустая строка или пробелы считаются незаполненным значением.
- После заполнения проверьте `missing`: если список не пуст, текст содержит незакрытые подстановки, и отправлять его рано.

## Почему неизвестные подстановки остаются видимыми

Если значение не передали, `fillTemplate()` не удаляет `{{ключ}}` и не подставляет заглушку. Так в тексте сразу видно, что ответ неполный: например, `{{deadline}}` напоминает, что срок ещё не согласован. Одновременно ключ попадает в `missing`, чтобы его можно было собрать и проверить программно. Молчаливая замена на пустоту или на «уточним позже» выглядела бы как готовый ответ и скрывала бы пробел.

## Проверка библиотеки

```js
import { validateTemplates } from './src/templates/library.js'
validateTemplates() // { ok: true, errors: [] }
```

`validateTemplates()` проверяет уникальность `id`, наличие непустых полей `id`, `title`, `when`, `body`, формат `id` в kebab-case и отсутствие пустых подстановок вида `{{}}`.

Запуск только этих тестов:

```sh
node --test test/templates/library.test.js
```
