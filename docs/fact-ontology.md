# Онтология факта

Артефакт этапа 1. Без него невозможны версии, статусы и обещанные 20 минут: модель будет выдавать прозу, а приводить её в порядок придётся человеку.

## 1. Определение

**Факт** — одно проверяемое утверждение об архитектуре, у которого есть источник с версией и состояние.

Правила, которые нельзя нарушать:

1. Один факт — одно утверждение. Если в предложении два смысла, это два факта.
2. У факта всегда есть источник и версия источника. Факт без источника — не факт, а задача «уточнить».
3. Факт не содержит оценок («удобно», «оптимально», «надёжно») — только проверяемое содержание.
4. Факт не переписывается. Изменение — это новый факт, старый помечается заменённым.
5. Факт принадлежит функциональной области и, если применимо, компоненту.

## 2. Поля

| Поле | Обязательное | Что содержит |
|---|---|---|
| `id` | да | постоянный идентификатор, не меняется никогда |
| `claim` | да | одно предложение, проверяемое |
| `subject` | да | о чём факт: компонент, система, область |
| `relation` | да | тип связи: `интеграция`, `требование`, `решение`, `ограничение`, `владелец`, `срок` |
| `object` | зависит | второй участник связи или значение (для интеграций — целевая система) |
| `fo` | да | функциональная область |
| `source_type` | да | `страница КАФО`, `схема`, `письмо`, `протокол`, `требование`, `Jira` |
| `source_ref` | да | идентификатор источника: `page_id` и `version` для страницы; имя диаграммы и версия вложения; `message_id` и дата для письма |
| `confidence` | да | `высокая`, `средняя`, `низкая` |
| `status` | да | `предложен`, `подтверждён`, `заменён`, `отклонён` |
| `confirmed_by` | для подтверждённых | кто подтвердил |
| `confirmed_at` | для подтверждённых | когда |
| `valid_from` | да | с какой даты факт считается верным |
| `supersedes` | нет | какой факт этот заменяет |
| `superseded_by` | при замене | какой факт заменил этот |
| `created_at` | да | когда создан |

## 3. Состояния и переходы

```
предложен ──подтверждён──► подтверждён ──новая версия──► заменён
     │                          │
     └──отклонён──► отклонён    └──опровергнут──► отклонён (история сохраняется)
```

- **Предложен** — извлечён программой из источника, человек ещё не смотрел.
- **Подтверждён** — человек открыл источник и согласился. Только такие факты попадают в ответы и на комитет.
- **Заменён** — появилась новая версия; факт остаётся в истории, в ответы не попадает.
- **Отклонён** — источник не подтверждает утверждение или утверждение неверно. Не удаляется: нужен для разбора.

Правило: **в ответ идут только подтверждённые факты с актуальной версией источника.** Всё остальное — «требует подтверждения» или «история».

## 4. Замена и версии

1. Пришла новая версия страницы или схемы — программа ищет факты, которые она затрагивает.
2. Совпадение определяется по тройке `subject + relation + object` внутри одной функциональной области. Текст `claim` для сопоставления не используется: он может переформулироваться.
3. Если тройка совпала — создаётся новый факт со ссылкой `supersedes`, старый получает `superseded_by` и статус `заменён`.
4. Если тройка не совпала — факты **не** заменяются. Программа помечает «возможное противоречие» и отдаёт человеку: либо это новый факт, либо изменилась суть.
5. Массовая замена при росте версии запрещена: иначе либо теряются верные факты, либо остаются устаревшие.

## 5. Подтверждение

- Подтверждает архитектор, отвечающий за функциональную область; для сквозных интеграций — архитектор трайба.
- Обязательное подтверждение: перед отправкой обоснования на комитет и перед фиксацией решения.
- Подтверждение означает «я открыл источник и увидел это утверждение», а не «я согласен с решением».
- Целевое время: до 10 минут в день. Если больше — программа предлагает слишком много; порог подтверждений настраивается.

## 6. Хранение

Один факт — один файл Markdown с frontmatter. Пример:

```markdown
---
id: fact-2026-11-24-0007
claim: "Сервис платежей передаёт события в шину Kafka"
subject: "Сервис платежей"
relation: "интеграция"
object: "Kafka"
fo: "Платежи"
source_type: "схема"
source_ref: "page_id=123456; diagram=Платежи; version=4"
confidence: "высокая"
status: "подтверждён"
confirmed_by: "архитектор ФО Платежи"
confirmed_at: "2026-11-24"
valid_from: "2026-11-20"
supersedes: null
superseded_by: null
created_at: "2026-11-24T09:10:00+03:00"
---

Сервис платежей передаёт события в шину Kafka. Схема «Платежи», страница 1,
связь «Сервис платежей → Kafka», подпись «события».
```

Файл можно открыть в Obsidian: он останется обычной заметкой. Редактирование вне программы допускается, но программа при следующем запуске проверит поля и покажет, что изменилось.

## 7. Индексы

- по `subject` и `fo` — для карточки компонента;
- по `source_ref` — что изменится при новой версии источника;
- по `status` — очередь подтверждения и история;
- по `relation` — список интеграций, требований, решений.

## 8. Как факты используются в ответе

1. Ответ собирается только из подтверждённых фактов.
2. Каждое утверждение в черновике ссылается на `id` факта, а факт — на источник с версией.
3. Если для утверждения факта нет — пишется «требует подтверждения», а не догадка.
4. Если источник устарел — утверждение помечается, и в ответе появляется предупреждение со ссылкой на новую версию.

## 9. Метрики

| Метрика | Целевое значение |
|---|---|
| Доля подтверждённых фактов среди используемых в ответах | 100% |
| Доля фактов с источником и версией | 100% |
| Время подтверждения одного факта | ≤ 30 секунд |
| Ежедневное время подтверждения | ≤ 10 минут |
| Доля фактов, заменённых корректно (без потери верных) | ≥ 95% |

## 10. Антипаттерны

- Факт-абзац с несколькими утверждениями.
- Факт без версии источника («из письма» без даты и автора).
- Реплика одного участника «в целом согласен» как подтверждённое решение: это `предложен` до фиксации в КАФО.
- Массовая замена всех фактов страницы при росте версии.
- Удаление отклонённых фактов.
- Использование текста `claim` для поиска дублей.
